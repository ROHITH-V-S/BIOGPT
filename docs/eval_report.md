# BioGPT Explorer — Retrieval Evaluation Report

Does entity-aware re-ranking actually improve retrieval over plain vector
search? This report answers that with measurements rather than assertion.

**Reproduce:**

```bash
cd backend
python scripts/build_eval_corpus.py --suite general   # ~64 PubMed abstracts
python scripts/build_eval_corpus.py --suite hard      # confusable-sibling corpus
python scripts/run_eval.py --suite general
python scripts/run_eval.py --suite hard
python scripts/run_eval.py --suite general --backend local   # weak-encoder control

# Generation metrics. Needs a local Ollama — see note below.
python scripts/run_eval.py --suite general --judge --llm ollama --judge-model gemma3n:e4b
```

`--backend` swaps the *encoder* while holding the chunks, questions and
re-ranker fixed, building and caching a matching index. `--llm` swaps the
*generator*. Local backends cost no API quota.

With Redis running (`make redis`) embeddings are cached per text, so re-running a
suite over an unchanged corpus costs **zero** API calls. That matters for
reproducibility as much as for cost: before, verifying a number meant spending
quota, so numbers tended not to get re-verified.

## Methodology

Corpora are built from **live PubMed abstracts**, not hand-written text, so the
retrieval task is realistic. All of a suite's topics are pooled into one index —
if each question were scored against only its own topic's abstracts, everything
in the index would already be relevant and precision would be ~1.0 for any
method.

**Retrieval metrics** (deterministic, no LLM involved):

| Metric | Definition |
|---|---|
| Context Precision@k | mean content-word overlap between each retrieved chunk and the gold answer |
| Context Recall | fraction of the gold context's vocabulary covered by the retrieved set |
| Hit@k | ≥1 retrieved chunk clears the relevance threshold (0.20 coverage) |
| MRR | mean reciprocal rank of the first relevant chunk |
| Queries reordered | how often re-ranking changed the result at all |

Overlap is computed on content words with stopwords stripped — otherwise "the",
"of" and "in" dominate and the metric mostly measures chunk length.

`Queries reordered` exists because of a failure this harness caught: a
re-ranker that never changes the order cannot change the score, and averaged
metrics hide that completely. It separates *no effect* from *bad effect*.

**Generation metrics** (faithfulness, answer relevancy) are LLM-as-judge and
opt-in via `--judge`. Their binary 0/1 verdicts are noisy; small differences
should not be over-read.

This pass runs against **locally served models**, for a reason that is not
primarily about cost. A full judge pass needs one answer plus two verdicts per
(question, context) pair across both modes — about 48 calls. OpenRouter's free
tier allows 50 requests *per day* in total, so the pass cannot complete there
alongside anything else; the first attempt died two-thirds of the way through.
Locally it is unmetered and repeatable, which is what makes the metric usable at
all. Two further consequences of running it locally:

- **The judge is a different model than the answerer** (`gemma3n:e4b` judging
  `llama3.2`). A model grading its own output is a known source of
  self-preference bias, and the single hosted fallback chain could not express
  that separation.
- **Answers are generated by a 3B model**, well below the hosted models the app
  uses by default. These figures characterise the *retrieval context*'s
  gradeability, not the quality ceiling of the deployed system.

Calls are batched by model — all answers first, then all verdicts — because two
models rarely co-reside in consumer VRAM and interleaving would force an
eviction and reload on every question.

### Two suites

- **`general`** — eight unrelated topics (TP53, mRNA vaccines, metformin,
  Alzheimer's, RNA Pol II, ACE2, BRCA1/2, CRISPR). Vector search can separate
  these on topic alone.
- **`hard`** — deliberately adversarial. Confusable siblings are pooled into one
  corpus (BRCA1 vs BRCA2, ACE vs ACE2, HER2 vs EGFR, Cas9 vs Cas12a, IL-6 vs
  IL-1), and each question turns on *which* member of the pair is correct. This
  is the setting where embeddings are supposed to fail and exact symbol
  matching is supposed to win.

Each suite is additionally run against **two other encoders** — MiniLM (384-dim,
weaker) and PubMedBERT (768-dim, biomedical) — as controls. The headline result's
explanation is that dense retrieval has already saturated, which predicts that a
worse encoder should give re-ranking room to help and a better one should give it
less. Six configurations (3 encoders × 2 suites) test that prediction instead of
asserting it. See [`retrieval_comparison.md`](retrieval_comparison.md) for how
the encoders compare to each other.

## Analysis

**Entity-aware re-ranking produced no meaningful improvement in any of the six
configurations tested** (3 encoders × 2 suites). Precision deltas are within
noise for an 8-question set, and the ranking metrics re-ranking is actually able
to move — Hit@3 and MRR — did not move at all, in any arm.

The reason is visible in the baseline column: dense retrieval **saturates**.
On the `hard` suite it scores Hit@3 = 1.000 and MRR = 1.000 — the correct chunk
is already at rank 1 for every question. Re-ranking cannot retrieve anything
new; it can only reorder what vector search returned. When rank 1 is already
correct, there is no headroom, and the best possible re-ranker is a no-op.

Notably this held even on the corpus built specifically to break embeddings.
The premise — that BRCA1/BRCA2-style near-synonyms confuse dense retrieval — did
not reproduce at this scale: a ~250-chunk corpus with k=3 is simply too small
for topical similarity to cause a miss.

### Testing the saturation explanation directly

"No headroom" is an explanation, not a measurement. If it is the right one, then
weakening the encoder should create headroom and re-ranking should start to pay.
That is a falsifiable prediction, so the same comparison was run across three
encoders — same chunks, same questions, same re-ranker, only the embedding space
changes:

| Suite | Encoder | Baseline Hit@3 | Precision@3 Δ | Hit@3 Δ | MRR Δ | Reordered |
|---|---|---|---|---|---|---|
| `general` | OpenRouter (2048d) | 0.875 | +0.006 | ±0.000 | ±0.000 | — |
| `general` | PubMedBERT (768d) | 0.875 | ±0.000 | ±0.000 | ±0.000 | 2/8 |
| `general` | MiniLM (384d) | 0.500 | **+0.024** | ±0.000 | ±0.000 | 4/8 |
| `hard` | OpenRouter (2048d) | 1.000 | +0.004 | ±0.000 | ±0.000 | — |
| `hard` | PubMedBERT (768d) | 1.000 | +0.003 | ±0.000 | ±0.000 | 3/8 |
| `hard` | MiniLM (384d) | 0.875 | ±0.000 | ±0.000 | ±0.000 | 1/8 |

**Hit@3 and MRR are unchanged in all six configurations — not small, exactly
zero.** The re-ranker was not idle: it reordered results on 1–4 of 8 queries in
every arm where that was tracked. It reordered, and the ranking metrics did not
move once.

The precision column is where the prediction partly holds. The largest gain,
4× any other, is on the weakest encoder — the one with the most headroom, as
predicted. So re-ranking does exploit headroom where it exists; it measurably
improves the *quality of chunks already retrieved*.

But it never converts a miss into a hit. Re-ranking only reorders the candidate
pool, and MiniLM's four `general`-suite misses are cases where no relevant chunk
is anywhere in that pool. **Re-ranking improves good retrievals; it cannot
rescue failed ones.** Those are different problems, and on this evidence only
the encoder fixes the second.

The `hard`/MiniLM arm adds a caution against over-generalising: there the weak
encoder produces no gain at all (every metric ±0.000, 1/8 reordered). "Weaker
encoder" does not reliably mean "more headroom".

The practical reading: entity-aware re-ranking is a **precision** intervention
that needs an encoder good enough to put a relevant chunk in the candidate pool
but not so good that it is already at rank 1. That is a narrow band, and none of
the three encoders tested sits inside it well enough to justify the complexity.

### Generation quality is unchanged too

With the judge pass now completing (it previously could not — see Methodology),
the generation metrics agree with the retrieval ones:

| | Faithfulness | Answer Relevancy |
|---|---|---|
| `general` — baseline / entity-aware | 0.875 / 0.875 | 1.000 / 1.000 |
| `hard` — baseline / entity-aware | 1.000 / 1.000 | 1.000 / 1.000 |

Both suites, both metrics: **±0.000**. Re-ranking changes what reaches the model
on 2–3 of 8 queries and the answers come out graded identically. That is the
expected consequence of Hit@3 and MRR not moving — if the relevant chunk was
already in context, reordering it does not give the model anything new to work
with.

Two details are worth more than the headline zeros:

**Relevancy is 1.000 while faithfulness is not.** The split is the point of
measuring both. The model always addresses the question asked; it does not always
do so from the supplied context. Answer relevancy alone would have reported a
perfect score for a system that was partly making things up.

**The single unfaithful answer is the query with the worst retrieval.** The one
0 verdict is TP53 on the `general` suite — precision 0.231, the second-lowest in
the suite, where the retrieved chunks discuss molecular docking of plant
compounds rather than p53 biology. Handed off-topic context, a 3B model answered
from parametric knowledge instead of abstaining. So the judge did not merely
confirm the retrieval metrics; it located where weak retrieval turns into an
ungrounded answer, which is the failure this whole pipeline exists to prevent.

That link is the practical argument for keeping generation metrics despite their
noise: precision @3 = 0.231 is an abstract number, while "the model fabricated an
answer for this question" is an actionable one.

### What the measurement caught

Building the harness was worthwhile regardless of the negative result, because
it exposed three real defects in the original re-ranker:

1. **Score saturation.** Raw match counts scored every candidate identically on
   5 of 8 questions (all six candidates mention "TP53"), so the stable sort was
   a silent no-op. Fixed with IDF weighting over the candidate set, so a term
   present everywhere contributes ~0.
2. **Rank information discarded.** Counting matches let a weakly-similar chunk
   leapfrog a strong one — this *actively hurt* the ACE2 query
   (precision 0.489 → 0.356). Fixed by fusing the normalised vector score with
   entity overlap (`VECTOR_WEIGHT = 0.7`) instead of replacing it.
3. **Discriminative terms thrown away.** Only *typed* entities were used, so
   "metformin" (matches no drug suffix) and "RNA polymerase II" (not a gene
   symbol) yielded nothing — 3 of 8 questions extracted zero terms and silently
   degraded to baseline. Fixed by re-ranking on all biomedical spans, typed or
   not.

After those fixes the re-ranker no longer regresses; it is simply unnecessary
at this corpus size.

### Honest limitations

- **8 questions per suite** is far too small for statistical significance. These
  deltas are directional at best.
- Overlap metrics are **lexical proxies**, not human relevance judgments. A
  paraphrase that shares no vocabulary scores 0.
- The relevance threshold (0.20) is a **judgment call**, not a calibrated value.
- Corpora are built from the same topic queries the questions come from, which
  guarantees the answer is present — an easier setting than open-domain
  retrieval.
- **Judge figures come from small local models** (`llama3.2` answering,
  `gemma3n:e4b` grading). They are directionally useful and reproducible, but a
  4B judge on 8 questions resolves nothing finer than "roughly the same". The
  harness reports which models produced each figure so the numbers are never
  read out of context.
- **A failed judge call is recorded as unscored (`--`), not as a 0 verdict.** The
  earlier behaviour counted an errored call as "unfaithful", which silently
  dragged the mean down in a way indistinguishable from a real negative. Runs now
  report how many questions were actually scored.

### Where re-ranking would plausibly earn its place

Conditions that would give it headroom. The second is now tested (above) and
only partly delivers; the rest remain untested here:

- **Corpus scale** — tens of thousands of chunks, where the correct passage is
  not already at rank 1.
- **Weaker embeddings** — *tested across three encoders.* The weakest quadruples
  the precision gain but moves Hit@3 and MRR not at all.
- **Underspecified queries** — where the embedding has less signal to work with.
- **Higher k with a strict token budget** — retrieve 50, re-rank down to 5. This
  is the most promising untested one, because it is the only setting where
  re-ranking's inability to retrieve anything new stops being a ceiling.

The honest conclusion is that this pipeline's bottleneck is not ranking.

### Correction: it is not corpus coverage either

An earlier version of this report concluded that the one `general` miss
(CRISPR-Cas9, Hit@3 = 0) failed because the corpus lacked a chunk stating the
mechanism — "and no re-ranker can fix that."

**That was wrong, and the embedding comparison disproved it.** Swapping only the
encoder, PubMedBERT retrieves a relevant chunk for that same question at rank 1
(precision 0.100 → 0.317, Hit@3 0 → 1) from the same 303 chunks. The evidence
was in the corpus the whole time; the general-purpose encoder failed to surface
it.

So the bottleneck on that query is the **embedding space**, not coverage and not
ranking. The lesson generalises past this one question: a retrieval failure
attributed to a missing document should be checked against a second encoder
before it is believed, because "not retrieved" and "not present" look identical
from the top-k alone. See
[`retrieval_comparison.md`](retrieval_comparison.md) for the full comparison.

This is also why the weak-encoder control above matters: saturation is a
property of the encoder, not of the task.
